0 — goal / non-goals

goal
One Worker URL = a full coding agent. Agent loop (pi harness) + virtual fs/shell/git (computer Workspace) + durable sessions, all inside DOs. Embeddable as an npm SDK, extensible like pi, wire-protocol compatible with a thin CLI/web client.
non-goals (v1)
· no containers, no local builds
· no python/node execution
· no multi-tenant auth/billing
· no TUI custom components
· no reimplementation of an LLM provider
Known limits, no further discussion: Workers CPU ~10ms per invocation (DO wall-clock is longer but still bounded — chunk tool output, stream partials, never block the loop on one long exec); no real processes — shell = just-bash isolate or container backend only when explicitly attached.

Decision: one DO per workspace, sessions namespaced inside

Nanocodex runs DO-per-session (js/managed/src/index.ts: DurableAgentSession, tables nanocodex_cloudflare_durability|agent|events). That is correct at their scale. For one-user self-deploy, one DO per workspace is simpler and still safe:

  • Isolation unit = workspaceId. env.AGENT.idFromName(workspaceId). All sessions in that workspace share one VFS (like one checkout, many branches) — matches the "one user, one repo" case.
  • Concurrency inside the DO is serialized by construction. DOs process one message at a time; a per-session promise-queue (nanocodex HostedNanocodex #queue pattern, examples/cloudflare-fetch-mcp/src/index.ts:64) prevents interleave between two prompts on the same session. Cross-session tool writes go through pi's withFileMutationQueue so edits don't interleave mid-file.
  • Scale-out later is a key change, not a rewrite: switch stub key to workspaceId:sessionId and add push/pull sync (computer already has this for the container backend). V1 skips cross-DO sync entirely.
Rule: local dofs SQLite inside the DO is the truth. Dynamic Workers (just-bash / worker-javascript) call back into host SQLite via WorkspaceServiceProxy — never a second store. Container backend (if ever attached) is the only remote-VFS case and needs explicit push/pull + watermark reconcile. Copied from computer's backend contract (packages/computer/src/backend.ts).

3 — core: persistence, fs, concurrency

3.1 session persistence (the money question)

  • Store = DO SQLite, two tables: pi_entries (the session tree: messages, tool calls/results, custom entries, lane/branch links) + pi_owners (fence + revision per session). Same-txn writes: every harness onUpdate event appends an entry before it is emitted on the socket. Socket is a view; storage is the truth.
  • Resume = replay. GET .../sessions/:sid/entries?after=n paginates the tree; WS reconnect replays from cursor. Pi's tree already supports lanes/branching — rewind/branch work over the wire for free.
  • Crash mid-run: tree is intact; open operations found via findOpenOperations (pi harness/session/types.ts) are marked interrupted on next open. Model calls are idempotent replays, tool calls are not auto-retried.
  • Fencing (from nanocodex store.rs): each connected client holds {ownerId, fence}; replace requires expected revision + live fence. Stale socket (e.g. phone + laptop) gets Fenced, never silently overwrites. Steer/abort go through the same fence.

3.2 filesystem

  • VFS = computer dofs (Database over DurableObjectStorageLike.sql, dofs/src/storage.ts, schema in dofs/src/schema). Mounts registry + mount-guard for read-only enforcement.
  • Git = workspace.git (computer docs/13_git_interface.md), exposed as POST .../sessions/:sid/git {argv}. No shell-quoting footguns; agent gets a narrow git tool, not raw git strings.
  • Seed/upload: PUT /workspaces/:id/files?path=... writes directly to VFS (clone-a-repo = push a tarball or sequential writes; no git clone inside the isolate in v1).

4 — tools: use pi's, not computer's

Computer's createAITools() (packages/computer/src/tools/ai.ts) targets the Vercel AI SDK. Pi expects AgentHarnessTool (TypeBox params + execute(id, params, signal, onUpdate, ctx)). Decision: pi's tools only, against a ComputerExecutionEnv.

// the only new code in the tool path (one file)
class ComputerExecutionEnv implements ExecutionEnv {
  // FileSystem: readFile/stat/readdir/writeFile/mkdir/rm/symlink/chmod
  //   → workspace.fs.*  (dofs/src/fs/filesystem.ts)
  // Shell: exec(cmd, cwd, env, signal, onUpdate)
  //   → worker-shell backend (just-bash, sync:none) OR container backend later
  // Git: status/diff/log/commit-ish → workspace.git (NOT shell strings)
}
  • Pi builtins wired: read, write, edit, bash (+ grep/find as shell commands in just-bash — no new tools needed in v1).
  • Computer's per-backend ExecBackendDescription text is reused: injected into the bash tool description so the model knows it is in an isolate shell.
  • Adapter risk is real but bounded: zod→TypeBox schema conversion and async-generator→onUpdate streaming happen in one adapter module, tested against the conformance harness (pi harness/session/testing/conformance.ts).

5 — wire protocol (control plane + stream)

POST /workspaces                          → { workspaceId }
POST /workspaces/:id/sessions             → { sessionId }
GET  /workspaces/:id/sessions/:sid        → metadata + recent entries (resume)
GET  /workspaces/:id/sessions/:sid/entries?after=n → paginate tree
POST /workspaces/:id/sessions/:sid/git    → { argv: [...] } via workspace.git
GET  /workspaces/:id/files?path=...       → file viewer / diffs
PUT  /workspaces/:id/files?path=...       → seed / upload
POST /workspaces/:id/exec                 → one-off shell outside agent loop

WS /workspaces/:id/sessions/:sid/stream
  client → server:  { type: "prompt", text } | { type: "abort" } | { type: "steer", text }
  server → client:  message_start/update/end · tool_start/update/end ·
                    agent_start/end · entry · get_commands · extension_ui_request

Mapping is 1:1. Every server frame is a pi harness event already appended to storage. tool_update carries streaming bash output (throttled, like pi bash.ts). entry is the persistence write itself — clients that store entries can resume offline.

6 — extensibility + embeddability (pi's best parts, kept)

Three embed layers (nanocodex lesson: be a library, not a service)

layershapenotes
L1 — SDKimport { createPiCf } from "pi-cf"
export class MyAgent extends createPiCf({ model }) {}		Composes Workspace DO + ComputerExecutionEnv + harness. Host brings own account + keys. Decided in phase 1; ~free since code is structured that way anyway.
L2 — extensionssame ExtensionFactory = (pi) => void contract as piInline (createPiCf({extensions:[myExt]}), = pi loadExtensionFromFactory) ships day one. VFS (.pi/extensions/*.ts in workspace, loaded via Dynamic Worker eval, sandboxed, git-versioned, per-workspace) ships after v1 core (~1.5–2d). npm-manifest form rides the same loader. Supported first: registerTool, registerCommand, event hooks, sendMessage/appendEntry. Deferred: ctx.ui components, raw pi.exec (→ virtual shell instead).
L3 — over the wireget_commands + extension_ui_request/response framesSame as pi RPC mode: web/CLI clients render extension UI without server changes.
Why this works on Workers: pi's extension runtime is pure data + async functions (handler registry); only the loader is Node-bound (jiti + node:fs). We keep the runtime contract, replace the loader (inline now, Dynamic Worker later).

P0 — skeleton (0.5d) — Worker router + empty Workspace DO + SQLite tables
wrangler config, withWorkspace DO, pi_entries/pi_owners schema, POST /workspaces round-trip. No agent yet.

Env adapter (fs→workspace.fs, exec→worker-shell just-bash, git→workspace.git); wire pi read/write/edit/bash; run headless prompt→tool→entry loop in DO; persist every onUpdate before emitting. Prove with POST /exec + one prompt over curl.
P2 — wire protocol (1–2d) — HTTP files/git/entries + WS stream
All endpoints in §5; fence + revision CAS; abort/steer; replay ?after=n; CLI client (prompt/abort/steer + frame printer) for verification.

createPiCf({model, tools, extensions}) DO factory; inline ExtensionFactory path; one sample extension (custom tool + command + hook) proving the contract.
P4 — VFS extensions via Dynamic Worker (1.5–2d, after v1 usable)
.pi/extensions/*.ts loaded with worker-javascript machinery (structured module graph, durable relative imports), sandboxed, RPC back to harness. npm-manifest form included.
P5 — hardening (ongoing) — caps, timeouts, web UI
Shell/output caps, per-session queues, minimal web client on the §5 protocol (entries replay + stream frames). No containers in v1.

9 — risks

  • pi import weight on Workers. pi-agent-core may drag node polyfills. Mitigation: import only packages/agent/src (harness+tools+session), never coding-agent app shell; bundle-check in P0.
  • Long exec vs CPU limits. just-bash chunk + throttle tool_update; kill via AbortSignal → ExecHandle kill; never await unbounded output.
  • DO SQLite growth. Entries table paginated + archived (nanocodex archived_sessions pattern); compaction = pi lane compact producing a summary entry.
  • What we explicitly do NOT solve in v1: real builds/tests in isolate, multi-user auth, container sync.

pi-do Frontend Plan

Grok-style multi-agent chat UI for frontend/web — React 19 + rsbuild, hono/SSE worker backend (untouched). UI only. Akeru-bot view layer as reference, bloub engine for avatars. Scope = full akeru roster + thread surface, nothing akeru doesn't ship.

Strategy — how we port

  • Contract-first. Before any parallel work, commit to main: shared types (lib/roster.ts types, thread/card view-model types), Tailwind v4 wiring, theme tokens, and empty directory scaffolding. Every worktree codes against these; nobody negotiates interfaces mid-flight.
  • Copy, then cut. Akeru components are copied into our tree first (with their MIT copyright header), then stripped of Effect/atom imports and rewired to our props/contracts. Never re-type from scratch, never port their state layer.
  • Verify on the running app, like a user. Every phase ends with a verify-web drive: launch, click through the changed surface, screenshot, assert visible state, zero console errors. Typecheck and rsbuild build are necessary, never sufficient. The verify-web skill is generated in Step 0 and maintained via /maintain-verification-skill at integration.
  • Fixtures are the API. Sidebar, groups, sections, presence, previews all read from lib/roster.ts. The open thread binds to the real bootstrapSession/useThread SSE stream. Swapping fixtures for live data later = one file.
  • Generate the project-local verification skill via /create-verification-skill: .cursor/skills/verify-web/ with launch (rsbuild dev + worker on 8787), doctor, drive recipe (browser automation: selectors, clicks, screenshots, console-error capture), evidence location, cleanup. Seed the feature map from the current app (thread, composer) and extend it as phases land.

Parallelization — worktree plan

Four phases run as three parallel worktrees + one. Step 0 lands on main first; everything branches from it. All four phase worktrees can start the same day.

Contracts, Tailwind, scaffolding, fixtures seed.

Merge in dependency order, integrate, smoke test, ship.

Worktree mechanics

  • Create: git worktree add .worktrees/wt-avatar -b wt-avatar main (repo already uses .worktrees/).
  • Each worktree: own npm install in frontend/web; own dev server on a distinct port (rsbuild dev --port 3001/3002/3003/3004) so agents verify visually without clobbering each other.
  • The worker (localhost:8787) is shared — one instance, already running as process worker. CORS already allows the 3000–300x localhost origins pattern (extend allowlist if a new port is added).
  • Merge with git merge in order; rebase a worktree on main if a later-merged sibling touched shared files.

Cross-worktree coordination

  • Subagents coordinate via hub messages, not by reading each other's worktrees.
  • wt-shell codes sidebar rows against BotAvatarProps with a static placeholder SVG; swaps to real BotAvatar at merge time (one import line).
  • wt-thread and wt-composer are fully disjoint (timeline vs composer) — zero shared files beyond Step 0 contracts.
  • If a contract proves wrong, the discovering agent messages the integrator; contract change lands on main, others rebase. Never negotiate inside a worktree.

Verification plan — self-verification loop

Principle: typecheck and build are not proof. Proof is the app running, driven the way a user drives it, with captured evidence. The loop lives in a project-local skill so every agent verifies identically, in this session or the next.

The verify-web skill (generated in Step 0 via /create-verification-skill)

  • Launch: rsbuild dev (port per worktree) + shared worker on 8787; readiness = port answering + build banner.
  • Doctor: process up, port owned, worker reachable, page loads without console errors.
  • Drive: browser automation with stable selectors (data-testid on new components — akeru does the same); clicks, typing, waits on visible state, never blind sleeps.
  • Evidence: screenshot per step + console-error log + asserted visible state, stored under a named evidence dir; cleanup never deletes evidence.
  • Feature map: one file per user-facing feature (sidebar search, bot create, thread send/stream, attachments, approvals, composer drafts…), each with the user-POV path, drive recipe, and the observable end state that proves it.

Per-phase loop

  1. Implement → typecheck + build (necessary, not sufficient).
  2. Drive the changed surface with verify-web: real user paths, screenshot each interaction, assert visible outcomes.
  3. Interaction checks: hover/focus states, empty states, error paths (worker down, stream drop), double-submit, keyboard nav, console clean.
  4. Bug found → reproduce on the driven surface first, fix root cause, re-drive until green. Receipts (screenshots + console log) attached to the phase report.

Upkeep

  • New UI surface lands → feature map gains a file in the same PR (the map rots otherwise).
  • At integration: full /maintain-verification-skill pass — source wave + live pass over every feature.

Per-worktree specifics

  • Each worktree verifies on its own port against the shared worker; evidence per worktree.
  • Phase 1 additionally: throwaway render harness comparing bloub React output against refs/bloub Vue demo states (same sample(t) calls → same paths).
  • Phase 3: live conversation against the real worker — bubbles, stream, typing, cards all observed.
  • Integration: full verify-web click-through on localhost:3000 + tsc --noEmit + rsbuild build.

Risks

Akeru components are deeper-coupled than they look. Some "view" files import atoms/commands internally. Mitigation: copy → strip → rewire is scoped per component; if a component exceeds ~2h of decoupling, rebuild it thin against our contracts using akeru only as visual reference.
bloub renderer port subtle bugs. Mask/paper layering is finicky (eyes are holes; back arcs must not show through). Mitigation: engine copied verbatim; only the ~250-line renderer is new; compared frame-by-frame against the Vue demo.
Thread view-model mismatch. Our SSE entries may not carry tool-status data the cards need. Mitigation: Step 0 maps actual useThread entry shapes first; cards render whatever exists, degrade gracefully — no backend changes to invent fields.
Tailwind v4 + rsbuild friction. Version compat issues possible. Mitigation: proven in Step 0 alone before anyone branches; fallback is CSS-modules per component (slower, decided only if Step 0 fails).

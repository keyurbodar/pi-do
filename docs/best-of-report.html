pi-cf: best-of report

Backend only — no frontend/UI. Sources: akeru-bot (T3 fork, Effect-TS + Mastra + provider CLIs, event-sourced SQLite), OpenMausBot (framework-free CLI-driver harness, node:sqlite + FTS5), Noodle (Swift, disk-as-message-bus, persistent bots + shared VMs), herdr (Rust terminal multiplexer for agent CLIs, keystroke-injection A2A), Grok Bot (public product facts: one shared cloud computer per account, inbox wake-ups, routines, per-bot memory). Research artifacts cloned at /tmp/grok-research/.

1 · Verdict up front

pi-cf's durability core (DO SQLite entry tree, runs ledger, chunk log, alarm recovery, transactional compaction) is stronger than all four — none of them owns its own loop, storage, and recovery the way pi-cf does. The gap is the opposite direction: pi-cf is an on-demand harness; the others are always-on teammates. The build plan below closes exactly that gap, borrowing only patterns proven in at least one shipped codebase.

5 · Add to pi-cf — best-of picks

5.1 Routines — scheduled durable turns from Grok Bot + akeru

  • pi_routines table: schedule (once / interval / weekdays / monthly), prompt, target session, expiry, max-active, min-interval floor (Grok Build's limits are good hygiene even in Bot terms).
  • One new alarm-mux job type enqueues a prompt into the existing turn pipeline — fence, runs ledger, recovery, budgets all come free.
  • Claim-based single-owner runs (akeru's RoutineClaim pattern) so a restarted isolate never double-fires.
  • Heartbeat scheduling per Noodle: persisted last-activity wins, consume exactly one overdue beat, no catch-up storms after downtime.

5.2 Bot inbox — async peer messaging from Noodle + Grok Bot

  • Durable pi_inbox table per session; pull, not push: deliver = persist row + inject a one-line wake sentinel into the bot's prompt (Noodle's <noodle-event/> pattern); the bot reads its inbox during the turn.
  • Idempotent delivery via client-supplied request UUID (Noodle) — dedupe across retries.
  • Wake-on-alarm: a message wakes a bot that's offline (this is Grok Bot's "a Bot wakes, processes, and can reply later"). Reuses the routines alarm plumbing.
  • Handoffs are visible: delivery, reads, and replies are entries — no hidden coordination (matches Grok Bot's "handoffs are visible" and Noodle's disk-as-bus auditability).
  • Ack gate (from herdr's two-phase prompt wait): optional reply-or-deadline acknowledgment on send — the sender's call can block until the recipient's outcome entry lands (wait by monotonic cursor, herdr's state_change_seq pattern) or a timeout fires. "Delivered" is not "acted on"; the ack layer is the pi-cf-native version of --wait --until blocked.
  • No orchestrator: coordination is emergent (Noodle's group model); a "chief of staff" is just a bot whose prompt says so.
  • Spawn-by-message (Grok Bot's "I'd spin up a dedicated agent"): a bot never gets raw session-create power. Addressing a not-yet-existing session name materializes it on first message — body = role description filled into a per-workspace backstory template. Creation is an inbox side effect: durable, visible as an entry (who spawned whom and why), rate-limited by the existing budgets machinery. No new execution concept, no spawn storms.
  • Channels are threads: a "channel" is inbox rows sharing a thread key; a bot "in" a channel means its context builder includes that thread's recent rows. No channel or membership tables.

5.3 Persistent-bot identity from Noodle + Grok Bot

  • A bot = session with a backstory: per-session system prompt content (name, role, standing instructions) resolved at session create — rides the §2 prompt-seam change.
  • Backstory stored as data, user-editable, merged with managed instructions so updates don't clobber user edits (Noodle's managed-AGENTS.md pattern).
  • Per-bot identity is the unit that owns routines and inbox — not the workspace (Grok Bot: memory/routines per Bot, workspace shared).

5.4 Context & compaction polish from akeru + pi

  • Surface context-window state as structured meta fields: usedTokens / contextWindow / compactionPending / summarySource (akeru ingests exactly this shape from its CLIs; we already store it).
  • Compaction custom instructions on the compact route (~5 LOC, pi supports it, pi-cf doesn't yet).
  • Nothing else — compaction stays as is; it leads every implementation studied.

5.5 Deliberately deferred

  • defer Worktree/workspace isolation — build only if soak shows real contention; then it's git-merge through existing routes, not new storage.
  • defer Memory (§4) — revisit after routines + inbox ship, since Grok's own pre-compaction flush and routine continuity both become natural once those exist.
  • defer Turn-context replay classification (OpenMaus's four preambles) — pi-cf's entry tree already resolves discontinuities structurally.

What the world looks like after #4

  • A workspace is a team desk: named bots (sessions with backstories) share one VFS; safety = existing mutation queues.
  • Routines fire turns while the user is away; budgets and recovery hold under kill -9 as proven.
  • Bots message each other and users through durable inboxes; group threads are visible, auditable entry trees; chiefs assign work with deadlines and get acks.
  • Chiefs can spin up new teammates by message, with creation visible and rate-limited.
  • Compaction, overflow recovery, and steer semantics are unchanged — already ahead of every implementation studied.

Open door after #4 (in priority order, none started)

  • Frontend/UI — explicitly pending by decision. Renders entries, inbox rows, meta fields; requires no backend changes.
  • Memory — Grok's pre-compaction flush and routine continuity become natural once routines + inbox exist.
  • Isolation — only if soak shows real contention on the shared desk.
